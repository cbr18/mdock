# ТЗ: Self-hosted markdown vault server

## Идея одной фразой

Своё приложение "как Obsidian, но с сервером": папка с md-файлами, веб-морда для просмотра/редактирования, git как локальная история и слой безопасной фиксации изменений, WebDAV — чтобы подключать Obsidian с телефона/десктопа.

## Принцип разработки

Делаем **инкрементально, две фазы**. Фаза 1 закрывает личное и семейное/self-hosted использование: несколько пользователей, у каждого по умолчанию есть свой personal vault, несколько устройств на пользователя, web UI + Obsidian через WebDAV. Фаза 2 — опциональная, только если реально понадобится shared vaults или совместное live-редактирование одного документа несколькими людьми.

Фаза 1 должна быть самостоятельной и полезной без Фазы 2. При этом нижний слой хранения должен быть спроектирован так, чтобы позже можно было добавить sharing/CRDT поверх, не переписывая работу с vault, git и файлами.

## Архитектура

Используем слоистую архитектуру. Слои должны быть разделены по ответственности:

- `config` — env/config parsing, static runtime settings.
- `store` — SQLite runtime-state: users, sessions, vaults, vault memberships, locks, future app-passwords/share metadata.
- `vault` — безопасная работа с файлами внутри конкретного vault: path traversal protection, `.git` deny, read/write/list/file operations.
- `git` — системный `git` через CLI, git init/status/add/commit/recovery, одна очередь git-задач на vault/repo.
- `locks` — лёгкие advisory locks для координации активных writes/edit sessions внутри одного vault.
- `webdav` — WebDAV adapter поверх `vault`, `locks` и `git`.
- `server` — HTTP/API wiring, auth middleware, routing, request/response boundaries.

Слои не должны смешиваться:

- `vault` не должен знать про HTTP/WebDAV.
- `git` не должен знать про HTTP/WebDAV/auth.
- `server` и `webdav` вызывают `vault`, `locks` и `git` через сервисные интерфейсы.
- один vault = отдельная папка = отдельный git-репозиторий = отдельная git queue.
- пользователь и vault — разные сущности; доступ задаётся через membership.

## Фаза 1 — Multi-user Isolated Vaults, Git-based MVP

### Функционал

- [ ] Инициализация root-папки для пользовательских vault на старте приложения.
  - Root-путь для vault задаётся через параметры запуска/container env.
  - Для Docker путь должен удобно задаваться через `.env`.
  - UI выбора папки в MVP не нужен.
- [ ] Пользователи, vaults и изоляция:
  - `user` и `vault` — отдельные сущности;
  - доступ пользователя к vault задаётся через `vault_members`;
  - при создании пользователя в MVP автоматически создаётся personal vault;
  - пользователь получает роль `owner` в своём personal vault;
  - физически каждый vault лежит в отдельной папке внутри `VAULTS_ROOT`;
  - каждый vault является отдельным git-репозиторием;
  - в MVP пользователь видит только vaults, где он member;
  - shared vault creation и управление участниками не входят в Фазу 1, но схема должна быть готова к этому.
- [ ] Веб-морда:
  - Дерево файлов как файловый браузер Obsidian.
  - Просмотр/рендер markdown.
  - Редактирование markdown в source mode.
  - Live-preview отдельной панелью рядом с редактором.
  - Базовые операции с файлами и папками: создать, переименовать, удалить, переместить.
  - Загрузка и управление вложениями/attachments, если они лежат внутри vault.
- [ ] WebDAV-сервер, отдающий содержимое той же папки для подключения Obsidian с телефона/десктопа.
  - WebDAV path в Фазе 1: `/webdav/<vault-slug>/`.
  - Пользователь может работать только с vaults, где он member.
  - Для MVP default WebDAV target — personal vault пользователя.
  - WebDAV использует Basic Auth с тем же логином/паролем, что web.
- [ ] Git-слой:
  - Рабочая директория каждого vault = отдельный git-репозиторий.
  - В MVP git remote не обязателен: достаточно локального репозитория в папке каждого vault.
  - Remote backup/sync добавить отдельной функцией позже.
  - Автокоммит при сохранении из веб-редактора с дебаунсом.
  - Автокоммит изменений от WebDAV/external writes через `fsnotify`.
  - Одна очередь git-задач на каждый vault/repo: worker-горутина последовательно обрабатывает git-операции и даёт эффект mutex внутри конкретного репозитория.
  - Группировка изменений в коммит через debounce-window: несколько изменённых файлов от одного источника коммитятся вместе.
  - Если при старте `git status` dirty, приложение делает recovery-коммит всего накопленного состояния, после чего продолжает работу из чистой рабочей директории.
  - Коммиты идут последовательно в `main`.
- [ ] Минимальные лёгкие локи:
  - Локи нужны только для предотвращения очевидной одновременной записи в один и тот же файл внутри одного vault.
  - Локи не должны блокировать чтение.
  - Локи не должны блокировать независимые файлы.
  - Локи не должны блокировать весь vault или git queue.
  - Лок на весь файл, без диапазонов строк.
  - Web UI берёт explicit lock только при входе в режим редактирования файла, не при обычном просмотре.
  - Лок поддерживается heartbeat-ом и коротким TTL.
  - Лок освобождается при закрытии редактора или по таймауту.
  - WebDAV write в файл, залоченный активным web editor другого owner/editor, получает `423 Locked`.
  - Короткие WebDAV write операции могут брать transient lock только на время самой записи.
  - Conflict branch для WebDAV в MVP не используется, потому что Obsidian не покажет нормальный merge UI.
  - Web UI должен показывать, что файл залочен другим источником/сессией.
- [ ] Встроенная авторизация:
  - Web: login form -> server-side session cookie.
  - WebDAV: Basic Auth на `/webdav/`.
  - Web и WebDAV используют одну таблицу пользователей и один источник правды по паролям.
  - Отдельные app-passwords для WebDAV не нужны в MVP, но могут быть добавлены позже.
  - Nginx/Authelia/Authentik могут быть описаны в README как внешний рекомендованный слой TLS/reverse proxy, но приложение не зависит от них и не делегирует им auth.

### Markdown MVP

- [ ] Рендер GitHub Flavored Markdown:
  - таблицы;
  - чеклисты;
  - зачёркивание;
  - fenced code blocks.
- [ ] Frontmatter:
  - YAML frontmatter парсится;
  - в MVP достаточно рендерить его как метаданные, без бизнес-логики поверх.
- [ ] Syntax highlighting для code blocks.
- [ ] Не входит в MVP:
  - wikilinks `[[Page]]`;
  - backlinks;
  - embeds `![[image.png]]`;
  - Mermaid;
  - граф знаний.

Эти Obsidian-фичи требуют отдельного парсинга связей между файлами и выносятся в отдельные задачи после базовой функциональности.

### Технологический стек

Подробный список библиотек и инструментов зафиксирован в [tech-stack.md](tech-stack.md).

- Backend: **Go**.
  - Git: системный `git` через `os/exec`, не `go-git`, потому что нужен полноценный merge/conflict behavior как в терминале.
  - WebDAV: ручной MVP handler на `net/http` для методов, нужных Obsidian.
  - File watching: `fsnotify`.
  - SQLite для runtime-state и auth.
- Frontend: React + CodeMirror 6.
  - Source-mode markdown editor.
  - Preview-панель рядом, без WYSIWYG.
  - В разработке frontend запускается отдельно через Vite dev server с hot-reload.
  - Go backend запускается отдельно; связь через CORS или Vite proxy.
  - В релизе `npm run build` собирает статику, а Go встраивает её в бинарник через `embed.FS`.
  - Конечный пользователь получает один бинарник.
- Хранилище:
  - обычная файловая система;
  - отдельный git-репозиторий внутри каждого vault;
  - SQLite рядом с приложением или в отдельном data-dir.

### SQLite

SQLite обязателен начиная с MVP, потому что users, sessions, vaults, memberships и locks — runtime-state, а не конфигурация.

В SQLite храним:

- пользователей: login, password hash, timestamps;
- vaults: id, slug/name, kind (`personal` или `shared`), path, created_at;
- vault_members: vault id, user id, role (`owner`, `write`, `read`), created_at;
- web-сессии: token/session id, user id, expiry;
- file locks: vault id, file path, owner/editor id, source, expires_at, heartbeat timestamp;
- conflict metadata, если позже появятся conflict views;
- app-passwords, если позже понадобятся отдельные пароли для WebDAV-устройств.

В config/env остаётся только статическая конфигурация запуска:

- root-путь к пользовательским vault;
- путь к data-dir/SQLite;
- host/port;
- путь к `git` binary;
- debounce intervals;
- lock TTL;
- cookie/session настройки;
- режим разработки/production.

SQLite должен включать WAL mode:

```sql
PRAGMA journal_mode=WAL;
```

Это нужно сразу, потому что web, WebDAV, fsnotify и git worker будут параллельно читать/писать runtime-state.

### Docker/config

- Приложение должно удобно запускаться в Docker.
- Все основные параметры должны задаваться через env.
- `.env` должен быть удобным способом настройки docker-compose/dev deployment.
- Vaults root и data-dir должны быть отдельными volume/bind mount.
- Git remote backup/sync не входит в MVP, но конфигурация не должна мешать добавить его позже.

### Безопасность путей и файлов

- Все файловые операции должны быть ограничены корнем конкретного vault.
- Запрет выхода за пределы vault через `../`, symlinks или path traversal.
- Запрет прямой работы web/API/WebDAV с `.git`.
- Нужно явно определить политику скрытых файлов.
- Web editor должен редактировать только поддерживаемые текстовые файлы.
- Бинарные файлы и attachments можно хранить и отдавать, но не открывать как текст.
- Нельзя логировать пароли, session tokens, auth headers и содержимое приватных файлов без явной необходимости.

### Результат Фазы 1

Рабочий self-hosted сервер заметок: несколько пользователей могут заходить со своих устройств через web UI или Obsidian/WebDAV, у каждого есть personal vault/repo, изменения безопасно фиксируются в git, параллельные правки одного файла не перезаписывают друг друга молча, доступ защищён встроенной авторизацией. Архитектурно vault уже отделён от user, чтобы позже добавить shared vaults без переписывания хранения.

## Фаза 2 — Multi-user Real-time Co-editing

### Когда делать

Только если появится реальная потребность: shared vaults, sharing отдельных папок/документов или несколько разных людей редактируют один документ одновременно live, как Google Docs.

До завершения Фазы 1 Фазу 2 не проектируем в деталях. Важно только не зашить архитектуру так, чтобы vault/git слой был непереиспользуемым.

### Что добавляется поверх Фазы 1

- [ ] Shared vault creation и управление участниками.
- [ ] Sharing документа/папки между vaults или пользователями.
- [ ] Права доступа: read/write.
- [ ] CRDT-слой для документов, открытых на совместное редактирование:
  - библиотека: **Yjs**;
  - frontend binding к CodeMirror/ProseMirror;
  - транспорт: WebSocket relay-сервер на Go или отдельный `y-websocket`;
  - сервер не парсит содержимое CRDT-сообщений, а релеит бинарные апдейты между клиентами;
  - периодическая сериализация текущего CRDT-состояния в markdown text -> коммит в git как snapshot.
- [ ] Presence UI опционально.

### Архитектурное решение

CRDT применяется **только к документам в режиме совместного редактирования**. Документы, которые не расшарены для live co-editing, продолжают жить в vault + lightweight file-lock + per-repo git queue модели Фазы 1.

### Открытые вопросы Фазы 2

- Права доступа на уровне документа, папки или vault?
- Нужен ли presence UI или достаточно совместного merge без визуализации?
- Сколько одновременных пользователей на документ ожидается?
- Где хранить CRDT updates/snapshots: рядом с md, в SQLite или отдельном хранилище?
- Как представлять shared-документ в git: копия/ссылка/отдельный shared repo?

## Авторизация

### Фаза 1

- Auth реализует backend приложения.
- Web использует login form и server-side sessions.
- WebDAV использует Basic Auth.
- Web и WebDAV проверяют один и тот же логин/пароль по одной таблице пользователей.
- Пароли хранятся только как хэши: bcrypt или argon2.
- JWT в MVP не используется.
- Nginx перед приложением может делать TLS termination и reverse proxy, но не является auth layer.

### Фаза 2

- Добавляются роли/права доступа.
- App-passwords для WebDAV можно добавить, если понадобится отзывать доступ с отдельного устройства без смены основного пароля.
- Внешние auth-системы вроде Authelia/Authentik можно рассмотреть как интеграцию, но базовый продукт должен работать без них.

## Шифрование — позиция проекта

- **В самом приложении шифрование данных at rest не реализуем**.
- Это осознанное решение ради простоты: app-level encryption ломает git diff, поиск по содержимому, обычный дебаг и совместимость с внешними инструментами.
- В README указать рекомендации:
  - HTTPS обязателен, если сервис доступен из интернета, иначе логин/пароль и содержимое идут открытым текстом;
  - LUKS/шифрование диска рекомендовано, если есть риск физической кражи сервера/диска;
  - end-to-end encryption не поддерживается и не планируется;
  - для паролей, финансов и других особо чувствительных данных лучше использовать специализированный инструмент, например Vaultwarden.

## Масштаб

- Фаза 1 рассчитана на несколько пользователей, personal vaults и несколько устройств на пользователя.
- Git на текстовых файлах лёгкий; узкое место — конкурентные git-операции, поэтому используется одна git queue на каждый vault/repo.
- SQLite с WAL достаточно для runtime-state MVP.
- Совместное редактирование одного документа несколькими пользователями не является целью MVP.

## Железо / инференс

AI/RAG поверх vault не входит в базовый проект. Если позже понадобится агент по заметкам, это отдельная функциональность поверх готового vault storage.
